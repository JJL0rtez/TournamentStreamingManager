# Operator architecture and independent recordings (v17)

## Installation
Extract the cumulative archive at the project root. Run `npm run typecheck`, `npm run build`, and `npm run test:all` separately. Existing settings and recordings are not included or replaced. The independent recording mode is opt-in; default behavior remains unchanged.

## Independent recording pilot
On the capture PC, stop all captures and relays before restarting the Node service with `TOURNAMENT_DYNAMIC_RECORDING=1` in its environment. In PowerShell, set `$env:TOURNAMENT_DYNAMIC_RECORDING="1"` and run `npm run dev:node` in that same terminal. Use a second terminal for the dashboard. With this setting enabled, newly started standalone production captures continuously generate a separate recording-quality H.264/AAC output on a private loopback TCP connection. The recording sink drains it and creates a unique segmented Matroska recording only when requested. Starting or stopping the sink does not change the USB source or YouTube relay. Disk backpressure terminates the recorder rather than blocking capture. Diagnostic and distributed ownership modes retain their existing behavior. The recording encoder consumes resources even when a disk recording is not active. This is intentionally disabled by default until DirectShow, NVENC and multi-camera throughput are validated.

First test a private/unlisted broadcast on one camera: stream only, start recording, wait, stop recording, confirm external playback remains continuous; repeat recording and inspect both files for audio, video, frame rate and duration. Repeat with a second identical camera and then all intended cameras. Verify prolonged recording and recovery from USB, network and disk errors. To roll back, stop outputs and restart the service without the environment flag. Do not first enable this mode at a live tournament.

## Operator workspaces
Live Operations shows the event summary, cameras, output controls, active alerts and live health. Tournament Setup edits assignments and event information. Settings has device/network, recording drive/hardware and access/licensing categories. Maintenance contains specialist diagnostics and reports. Successful assignment checks and successful readiness rows are suppressed; blocking issues and warnings remain visible. This is the first extraction pass on App.tsx: operator navigation, error display, alert history, microphone selection, and request coordination are now separate modules. The main App remains large and is not yet fully decomposed.

Device pairing prefers explicit persistent microphone IDs; ambiguous or missing assignments require operator correction instead of guessing. New session assignments may carry microphoneId, and legacy names are still supported when unique. Active banner and operations-history acknowledgement share local browser storage and events. This does not resolve the underlying issue, and formal incident resolution/audit records remain distinct. Requests through the shared API client coalesce identical in-flight GETs and never retry mutations. Hidden live panels, hardware/access panels and maintenance workspace are mounted on demand; not every historical panel's polling has been migrated.

Browser tests are isolated to avoid modifying runtime dependencies. Install on the target PC using `npm --prefix browser-tests install`, then `npm --prefix browser-tests exec -- playwright install chromium`, then `npm run test:browser`. Tests use a local Vite server and intercepted API calls, not physical cameras. They are supplied but have not been executed in this environment. The optional media unit test can be run using `$env:TSM_TEST_MEDIA="1"` followed by `node --import tsx --test tests/switchable-recording.test.mts`.
